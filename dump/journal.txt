Mike's answers (binding constraints for the whole library):
  A1 — Python modules + C modules; heavy work in C; not too many, not monolithic.
  A2 — C handles everything heavy for optimal performance.
  A3 — NO IMPORTS besides ctypes. No math module. The lattice IS its own math
       engine per guide §107–110. This replaces every math library.

Architectural consequences derived from A3:
  - No `import math`, `import cmath`, `import numpy`, `import mpmath`, `import
    fractions`, `import sympy`, `import scipy` anywhere in the Python layer.
  - No linking `libm` anywhere in the C layer.
  - All transcendentals implemented from scratch: exp via Taylor, ln via atanh
    series, sin/cos via reduced-argument Taylor, sqrt via Newton, pow via
    exp(e*ln(b)), atan via Machin-style, pi via Machin, etc.
  - Per Rule 33 ("no lists, everything dynamic"): the six base sublattice
    families, 12 FORCE families, 12 PHASE families, 42 combined states, 144
    FQG cells, LCM tower landmarks, and palindromic cascade are all computed
    dynamically from N and the prime sieve, never hardcoded. Only the true ET
    constants (N, S, K) and small literals (0, 1, 2, 3, 4) are hard-coded.
  - The Odrzywołek (2026) EML operator + Webb (1935) stroke + palindromic
    cascade together are the library's three foundational backbones per guide
    §109; everything mathematical in the library derives from these.
