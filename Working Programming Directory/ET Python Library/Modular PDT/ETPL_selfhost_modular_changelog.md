## 4. @ETPL:import Directive System

### 4.1 What It Is

The `// @ETPL:import <filename>` directive is a **preprocessing** instruction recognised
by the ETPL runtime before parsing. When the ETPL toolchain reads a `.pdt` file
containing these directives, it substitutes each one with the full contents of the
referenced file, building a single unified source string before the parser sees it.

This enables modular `.pdt` development: each of the 40 modules is a standalone file;
`ETPL_main.pdt` assembles them via `@import`.

**ET Derivation:**
```
P (individual module files)  ∘  D (@ETPL:import directives)  ∘  T (preprocessing traversal)
  =  E (unified .pdt source string ready for parsing)
```

### 4.2 Directive Syntax

```
// @ETPL:import <relative-or-absolute-path.pdt>
```

- The comment prefix `//` means the directive is **transparent** to any parser that
  does not support preprocessing — it gracefully degrades to a comment.
- Paths are resolved relative to the file containing the directive.
- The `ETPL_PROJECT_DIR` environment variable is searched as a fallback.
- `/mnt/project` and `os.getcwd()` are additional fallback search locations.
- Cycle detection prevents infinite loops (ET Traverser Finiteness, Eq 219).
- Maximum depth: 144 = MANIFOLD_SYMMETRY² (ET Traverser Finiteness, Eq 83 + Eq 144).

### 4.3 Changes Made to ETPL.py (Python Bootstrap Host)

Three additions to `ETPL.py` enable the `@ETPL:import` system. These are already
implemented in the delivered `ETPL.py` file (outputs directory).

#### 4.3.1 `ETPLParser._preprocess_imports()` — new static method

Added immediately before `parse_file()`. Performs the line-by-line substitution
of `// @ETPL:import` directives with file content. Features:

- 5-path search order: source_dir → bootstrap dir → ETPL_PROJECT_DIR → /mnt/project → cwd
- Cycle guard via `visited` set (pragma-once semantics)
- Gap reporting: `// @ETPL:import-gap <file> [ET: file not found...]`
- Cycle reporting: `// @ETPL:import-cycle <file> [ET: cycle suppressed...]`
- Depth reporting: `// @ETPL:import-depth-exceeded <file> [ET: max depth 144 reached]`
- Audit markers: `// @ETPL:import-begin <file>` / `// @ETPL:import-end <file>`

#### 4.3.2 `ETPLParser.parse_file()` — updated

Added preprocessing call between file-read and `self.parse(code)`:
```python
source_dir = os.path.dirname(os.path.abspath(filepath))
code = ETPLParser._preprocess_imports(
    code, source_dir,
    visited={os.path.abspath(filepath)}
)
```

#### 4.3.3 `ETPLInterpreter.interpret_file()` — updated

Added preprocessing call **before** `_process_preload_directives()` so that
`@ETPL:preload` annotations inside imported modules are visible to the preload processor.
Critical order: read → preprocess → preload → parse → eval.

## 6. True Self-Hosting Requirements

True self-hosting means the ETPL binary:
1. Is compiled **by ETPL** (not by Python)
2. Executes **without Python** at runtime
3. Can compile **another copy of itself** from `ETPL_main.pdt`

### 6.1 Closure Stages

| Stage | What it closes | Achieved by |
|-------|---------------|-------------|
| Stage 0 | Bootstrap: compile ETPL_main.pdt → ETPL binary | ETPL.py (Python host) |
| Stage 1 | Math C-extension | `ET_Math_Native.pdt` ✅ |
| Stage 2+3 | sys/posix/time/marshal C-extensions | `ET_Platform_Native.pdt` ✅ |
| Stage 4 | Module import system | `@ETPL:import` preprocessor ✅ |
| Stage 5 | All stdlib + third-party deps | 34 trace modules (pending) |
| Stage 6 | Full self-compilation: binary compiles itself | Goal of this modularisation |

### 6.2 What True Self-Hosting Forbids

- ❌ Assembly language fallbacks (objcopy, .s files) in ETPL_source.pdt
- ❌ C code generation paths in ETPL_source.pdt
- ❌ `import python_ast` at runtime in the compiled binary
- ❌ `import importlib` at runtime (trace_importlib.pdt closes this)
- ❌ `import marshal` at runtime (ET_Marshal + trace_marshal.pdt close this)
- ❌ `import math` at runtime (ET_Math_Native.pdt closes this)
- ❌ Placeholders, stubs, or `pass` bodies in the compiled path

All of the above are permissible in `ETPL.py` (the Stage 0 Python bootstrap host).

## 8. Common Translation Errors and How to Fix Them

### 8.1 Dotted names surviving translation

**Symptom:** `obj.attr` appears in executable code.  
**Cause:** Translator bug — `Attribute` nodes should produce `obj D attr`.  
**Fix:** Replace all `obj.attr` with `obj D attr` in executable code.

### 8.2 `import X` stubs that are not resolved

**Symptom:** `// @ETPL:unresolvable X` directive with no binding for `X`.  
**Cause:** Module unavailable at translate-time.  
**Fix:** For stdlib modules — add binding manually from the appropriate trace file
or mark as `// @ETPL:c-extension X [handled by trace_X.pdt]`.

### 8.3 Class `__init__` mangling collision

**Symptom:** Multiple classes define the same method; only one survives.  
**Cause:** Translator bug — class method names must be mangled `ClassName__method`.  
**Fix:** Ensure all class methods use `ClassName__methodname` form.

### 8.4 `while True:` translates to unbounded loop

**Symptom:** `∞ (body) (D Omega)` or `∞ (body) (D 0)`.  
**Cause:** Python `while True:` → must become `∞ (body) (D WHILE_LOOP_FINITE_BOUND)`.  
**Fix:** Replace with correct bound; ensure `WHILE_LOOP_FINITE_BOUND = 144` is defined.

### 8.5 `→ E` with no argument crashes parser

**Symptom:** `→ E` alone on a line.  
**Fix:** Replace all bare `→ E` with `→ E P`.

### 8.6 `√` generating `_math.sqrt()` instead of `_et_sqrt()`

**Symptom:** Runtime NameError on `_math`.  
**Fix:** Replace `_math D sqrt(x)` with `_et_sqrt(x)`.

### 8.7 `_et_` prefix missing from conflicting variable names

**Symptom:** ParseError — variable named `P`, `D`, `T`, `E`, `lambda`, `sum`, etc.  
**Fix:** Rename with `_et_` prefix.

### 8.8 Empty function body

**Symptom:** `D name = λ params .` with no body after the dot.  
**Fix:** Must be `D name = λ params . P` (at minimum — a P ground return).
