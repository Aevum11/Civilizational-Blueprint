#### 7.17.0 Three Tools Applied to the Testing System

**Identification Principle:** P = the EUDD production system under test (Manager, `.akashic` format, discovery engine, API, GUI, Omniscient watchdog). D = the test specifications — cases, criteria, thresholds, precision requirements — the finite constraints that define pass/fail. T = the test execution agent (C++ test harness, benchmark profiler, regression comparator) — the agency that navigates the test space and substantiates verdicts.

**Descriptor Gap Principle:** Every behavioral promise the EUDD document (§0–§12) makes IS a testable Descriptor. Any promise without a corresponding test case is a Descriptor Gap. This section closes all such gaps. The 15 test categories below were derived by exhaustive audit of EUDD v25 — every section maps to at least one test category; every test category maps back to at least one section.

**Subsumption Law:** The test suite subsumes every testable behavior the EUDD produces without remainder. Verification: §7.17.16 (Coverage Verification) confirms no section of the EUDD document lacks test coverage. The test suite itself is subject to the same principle — if a new feature is added to the EUDD, the test suite must extend to cover it.

#### 7.17.1 Test Infrastructure

**Framework:** C++ test suite using Catch2 (header-only, no external dependencies beyond the test binary). Catch2's `TEST_CASE` / `SECTION` / `REQUIRE` structure maps naturally to ET's {P, D, T} identification: each `TEST_CASE` identifies the substrate (P), each `SECTION` specifies constraints (D), each `REQUIRE` substantiates a verdict (T).

**Precision stack:** All verification computations use the same MPFR + GMP + FLINT/Arb stack as the production system. Verification precision: 361 dps (1200-bit), identical to production. Tests that verify precision behavior use the SAME precision — no separate "test precision" vs "production precision." The system IS the test, tested at the precision it operates.

**Test data:** No synthetic mock data. All test values are real ET values — the same bootstrap values (§3.17 + §3.18), the same verified projections from the Apéry investigation, the same `constants.py` values. The test suite operates on a real `Sempaevum.akashic` file generated by the bootstrap module. Tests that verify idempotency, memoization, and discovery operate on this real file.

**Test `.akashic` lifecycle:** Each test suite run generates a fresh `Sempaevum.akashic` via the bootstrap module (§7.7). Tests that modify the file run in defined order within their category. A clean copy is available for categories requiring pristine state. The bootstrap generation itself IS the first test (BSV-00).

**Test naming convention:** `[CATEGORY]-[NUMBER]` where CATEGORY is one of the 15 categories below. Example: `BSV-01` (Bootstrap Self-Verification test 1), `MEM-03` (Memoization test 3), `IDM-02` (Idempotency test 2).
